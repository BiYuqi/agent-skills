# 派卡与验收

分工：**子代理写代码，主会话不写业务代码，只验收。** 用户不需要每次说「派子任务、用便宜模型」——用了这个技能就是这么做。

本文中的路径都相对于仓库根目录；`<仓库根>` 指 `git rev-parse --show-toplevel` 的结果。

## 0. 先读项目的「任务配置」

本技能是通用的，项目差异全部来自项目根目录 `AGENTS.md` 的 `## 任务配置` 一节（格式见 `project-init` 技能的模板）：

| 配置项 | 用在哪 | 缺省值 |
|---|---|---|
| 卡号前缀 / 总表 / 卡片目录 | 第 1 步选卡 | `t` / `docs/TASK.md` / `docs/tasks/` |
| 子项目（可选） | 多项目仓库：按卡号前缀找总表、工作目录、检查命令 | 无 |
| 安装依赖 | 并行 worktree 里先装依赖 | 无（不装） |
| 提交前检查 | 子代理收尾、主会话验收 | 无，验收时提醒用户补上 |
| 验收红线 | 第 4 步审 diff 的项目专属清单 | 无 |
| 提交策略 | 第 5 步：`直接提交` 或 `先问` | `先问` |
| 写卡模型（可选） | 第 0.1 节，只影响 Claude Code | `sonnet` |

没有这一节：用缺省值继续，汇报里提醒用户「可以用 `project-init` 补上任务配置」。

项目的 `AGENTS.md`、全局规则（如 `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）和本技能冲突时，以项目和全局规则为准。

## 0.1 子代理怎么开（按你所在的工具）

子代理统一叫「写卡子代理」，任务内容一律用第 3 步的 prompt 模板。

| 工具 | 怎么派 | 怎么返工 |
|---|---|---|
| Claude Code | Agent 工具，`subagent_type: "general-purpose"`、`model: <写卡模型>`，description 写「做 <卡号> <卡片名>」。子代理在后台跑，等完成通知，不要轮询，不要提前猜结果 | SendMessage 发回同一个子代理 |
| Codex（CLI / App / IDE） | 子代理默认开启。派自定义代理 `card_worker`（用户级 `~/.codex/agents/card_worker.toml`，所有项目共用）；没装就派内置的 `worker` 角色，并提醒用户装一次（见第 0.2 节）；把第 3 步的 prompt 交给它。多张卡并行就一次派多个，等全部结果回来再验收 | 让 Codex 把问题清单发给同一个子代理线程（CLI 里用 `/subagents` 查看）；线程已关闭就新派一个，prompt 用第 3 步模板 + 问题清单 + 「在现有改动基础上修，不要推倒重来」 |
| 没有子代理能力的工具 | 不派。在本会话里按卡片自己做，写完后**另起一轮**严格按第 4 步验收，汇报里注明「作者与验收未分离」 | 自己改，再验一轮 |

- **验收一律由主会话做。**
- 写卡子代理的约束全部在第 3 步的 prompt 里，所以没有自定义代理也能派；自定义代理只是多了固定的身份和可选的便宜模型。
- 子代理不知道这段对话，只看得到它自己读到的文件。prompt 里不写「按刚才说的」，写清文件路径。

## 0.2 Codex 写卡子代理（用户级，装一次）

本技能目录下的 `codex/card_worker.toml` 是通用的 Codex 自定义代理定义，不含任何项目信息。装到用户级目录，所有项目共用：

```bash
mkdir -p ~/.codex/agents && cp <本技能目录>/codex/card_worker.toml ~/.codex/agents/
```

- 想让写卡用更便宜的模型：在 `~/.codex/agents/card_worker.toml` 里填 `model` 和 `model_reasoning_effort`。
- 沙箱、审批、MCP 从主会话继承，代理文件改不了。
- 不要把它放进项目的 `.codex/agents/`：项目差异只写在 `AGENTS.md` 的「任务配置」里。

## 1. 选卡

1. 读总表（多子项目时：参数是卡号就读对应前缀的总表；`next` 没指定时读所有总表）。
2. 参数是卡号 → 用它；参数是 `next` 或为空 → 选依赖全部 ✅、状态 ⬜ 的卡；有多张时，多子项目按配置里子项目表的顺序，同一前缀内取编号最小的。
3. 检查依赖：有依赖不是 ✅ 就停下，告诉用户缺哪张，不要派。
4. 卡已是 🔄：可能是上次中断的，先看 `git status` / `git log` 里有没有它的半成品，有就让子代理接着做（在 prompt 里说明），不要从头覆盖。
5. **派卡前体检**（每张卡一分钟）：卡片要用的依赖包、工具、前置文件（`必读` 里引用的上游代码、测试要 import 的包）是否已经存在，或者卡片「范围」里写明由它安装 / 创建。缺了又没人负责 → 先修卡片（加进本卡的范围和触碰文件，或补到负责的上游卡），再派；拿不准归属就问用户。
6. 一次派多张：只有它们的「触碰文件」完全不重叠才能并行；有重叠就串行，拿不准也串行。共用的接口定义（数据库表、消息格式）、依赖清单和锁文件都算重叠。并行时：
   - **不要用从远端分支切出来的自动隔离**（比如 Claude Code Agent 工具的 `isolation: "worktree"`，它从 `origin/<默认分支>` 切）：本地还没推送的提交（比如刚验收的上游卡）带不进去，子代理会发现依赖缺失。
   - 主会话手动建：`git worktree add -b task/<卡号> ../<仓库目录名>-worktrees/<卡号> <当前分支>`（放在仓库外，免得根目录的 lint 扫进去）。prompt 里写明工作目录是这个绝对路径，先在里面跑配置的「安装依赖」命令，不要改主目录。
   - 验收在各自 worktree 里做；通过后在 worktree 里提交，回主目录 `git merge --ff-only` 或 `git cherry-pick`，再 `git worktree remove` 并删分支。每合完一张，在主目录再跑一遍「提交前检查」，确认几张卡合在一起也没问题。

## 2. 开工

- 把总表里这张卡改成 🔄（这是主会话唯一动手改的文件之一）。
- 分支照项目规则来；项目没写就在当前分支上做，用户此前指定了分支就照用户的来。

## 3. 派给子代理

prompt 用下面的模板，把 `<…>` 填好。**不要把卡片内容抄进 prompt**，让它自己读文件——卡片是唯一来源：

```
你在 <仓库根绝对路径；并行时是对应 worktree 的绝对路径> 里完成任务卡 <卡号>：<卡片目录>/<文件名>.md。

开工前必须读完：根目录 AGENTS.md（全仓规则；多子项目时再读子项目的 AGENTS.md），然后读这张卡片，以及卡片「必读」里列的所有文档和章节。
<如果是接着做：上次已完成的部分见 git diff / 现有文件，在此基础上继续，不要推倒重来。>

要求：
- 只做卡片「范围」里的事，「明确不做」的一律不碰；只改卡片「触碰文件」里列的文件。确实需要改别的文件时，不要改，在最终报告里说明原因。
- 文档之间、文档与代码之间有冲突时，不要自己选一边，停下来在报告里写清楚冲突点。
- 不新增卡片没写的依赖。
- 密钥只从环境变量 / .env 读，不写进代码和测试；需要真实账号、Key 的步骤不要伪造通过。
- 新逻辑要有测试。
- 收尾前跑 <提交前检查命令；没有就写「卡片验收标准里能自动跑的命令」>，全部通过为止。
- 不要 git commit，不要改任务总表，不要勾卡片里的复选框——这些由验收方做。

最终报告（用用户的语言）包含：
1. 改动文件清单（新增 / 修改）
2. 逐条对照卡片「验收标准」：每条写 已验证（附命令和结果）/ 无法自动验证（原因）
3. 偏离卡片或做了假设的地方、遇到的文档冲突、想改但没改的文件
```

## 4. 验收（主会话的核心工作）

不信报告，自己核实。按顺序：

1. **跑检查**：「提交前检查」，以及卡片验收标准里能自动跑的命令。原样记录失败输出。
2. **范围核对**：`git status` + `git diff --stat`（含未跟踪文件），对照卡片「触碰文件」。多出来的文件逐个判断是否合理；动了其他卡负责的文件 → 不通过，除非子代理已说明且确有必要（这种要告诉用户）。
3. **逐条验收标准**：每条亲自验证（跑命令、读代码、写临时检查后删掉）。需要真实账号、真实 Key、手动看界面的，标「无法自动验证」，不要假装通过。
4. **审 diff**：
   - **项目红线**：任务配置里「验收红线」逐条核对；`AGENTS.md` 其他章节里的「必须 / 不许」也算。
   - **通用红线**：新依赖卡片没写 → 不通过；写了的确认许可证与项目要求相符；密钥、`.env`、本地数据没有进 git；没有绕过类型检查、关掉测试来「通过」检查。
   - 「明确不做」的事有没有被做了。
   - 改了架构（新目录、新模块、新接口、新依赖）是否同步了项目的架构文档。
5. **偏离要追到底**：子代理报告的、或验收中发现的任何偏离（路径、API、版本和文档不符，换了做法，发现文档没写到的坑），都要在 `AGENTS.md`、`docs/`、`README.md`、卡片目录里全文搜一遍（`grep -rn`）。会影响后续卡的，当场修文档，汇报里列出改了哪些；不能只写进本卡的验收记录了事。
6. **结论**：
   - **通过** → 进第 5 步。
   - **不通过但问题明确可修** → 把具体问题清单（文件:行号 + 期望）按第 0.1 节的返工方式交回去修，修完从 4.1 重新验收。最多返工 2 轮。
   - **返工 2 轮仍不过 / 问题要用户拍板**（文档冲突、要改别的卡的文件、要加依赖、范围有歧义）→ 停下向用户汇报，卡片保持 🔄。
   - 验收时发现的小问题（错别字、漏一条测试）也交回子代理修，主会话不亲自改代码。

## 5. 收尾

1. 勾上卡片里已完成的「范围」复选框；无法自动验证的验收项，在卡片末尾加一节「验收记录（YYYY-MM-DD）」如实写明：哪条、为什么没法验、怎么手动验。
2. 总表里改成 ✅。有未验项时仍可标 ✅，但必须写进验收记录，并在汇报里提醒用户手动验。
3. 改了开发命令或项目状态 → 确认 `README.md` 已同步（没同步就让子代理补）。
4. 提交，按任务配置的「提交策略」：
   - `直接提交`：验收通过就提交，汇报里给出提交哈希。
   - `先问`（缺省）：把本卡相关文件 `git add` 好，汇报里给出拟用的提交信息，用户同意再提交。
   - 提交信息 `feat(<卡号>): <卡片标题>`（文档类卡用 `docs(<卡号>)`），正文简述要点。项目或全局规则对提交信息另有要求（比如不加 AI 署名行）的，照规则来。
   - **推送一律要用户明确同意**，汇报里写明还有哪些提交没推送。
   - 验收标准里含「用户确认」的卡（如界面稿），用户确认前不提交，产物留在工作区；给用户挑选的多套方案、中间截图一律不提交。
5. 用户这次要的是连续做多张（如「把 MVP 做完」），回到第 1 步选下一张：依赖都 ✅、触碰文件不重叠的卡直接并行派出，不用问「要不要派下一张」；否则停下汇报。

## 6. 汇报（用用户的语言，简短）

- 做了哪张卡、结论（✅ / 🔄 卡住）
- 检查命令的结果
- 需要用户手动验证的项
- 子代理的偏离 / 假设、返工了几轮、需要用户决定的事
- 提交哈希（或待确认的提交信息）、未推送的提交；下一张可开工的卡

## 只验收模式

参数是 `验收 <卡号>`（或用户说「验收 t05」）：跳过 1–3 步，直接对当前工作区里这张卡的改动做 4–6 步。不通过时没有可续的子代理，就新开一个子代理，prompt 用第 3 步的模板并附上问题清单。
